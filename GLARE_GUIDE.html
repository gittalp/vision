VisionSim HDR Web 0.9.1

Choosing glare-analysis settings

A companion to the short help beside the controls. The bundled evalglare 3.06 engine, source calibration, and conversion mathematics are unchanged.

Start with a reproducible comparison

Keep the original HDR, lens projection, calibration, output size, sampling and command arguments with the result. Inspect the numbered source check image and the source table. A detected bright region is a model candidate, not a measurement of somebody's discomfort.

The default fixed-threshold path remains identical to version 0.9, including its explicit legacy low-light correction ON. To use the documented modern engine defaults deliberately, press Use documented engine defaults. This sets the correction OFF, source threshold 2000 cd/m2, peak threshold 50000 cd/m2 and merging argument 0.2 rad. It does not change source calibration, resolution, sampling, or your lux entry.

Version note: the supplied five-page manual identifies itself as v2.10 and says low-light correction is on. Wienold's 2024 update (page 7) says it is OFF since v2.14 because it can suppress DGP incorrectly for dark electrochromic glazing with visible sun. Both statements describe their respective documents; do not silently treat the older default as the modern default. [1,2]

Sampling and projection

ChoiceMeaning and use
1 sampleOne lookup at the output pixel center: quick inspection. Check the result against higher sampling when bright detail is small.
2 x 2Four bilinear source lookups per output pixel, with subpixel solid-angle weighting. The retained starting setting.
4 x 4Sixteen lookups. Compare when downsampling strongly or capturing narrow light strips, bright reflections, or sharp boundaries. Approximately four times the lookup count of 2 x 2, not necessarily four times total runtime.

These are application sampling choices, not evalglare's source-merging radius or a model of eye scatter. More samples can reduce aliasing but cannot recover clipped highlights, uncaptured sources or adequate spatial detail from an undersized output. Compare source counts, source luminance and solid angle, as well as illuminance and glare metrics; stable illuminance alone does not establish stable source segmentation.

An actual equidistant/angular -vta input does not require a different radial projection family. Nevertheless this release still prepares a new standardized angular raster: it may resize, recenter and subpixel-sample the image, then write neutral RGB encoding of calibrated luminance with normalized exposure. It is not a byte-for-byte passthrough. Equisolid input undergoes actual nonlinear reprojection. Always select the real projection; changing a header is not changing a lens. [3,4]

Three different controls, not three interchangeable thresholds

ParameterWhat it controlsStarting point and interpretation
Source threshold -bWhich pixels become glare-source candidates.2000 cd/m2 is the published fixed default, not a comfort limit. Lowering it includes more pixels; raising it includes fewer. A task-derived reference is an alternative. [1,2]
Peak extraction -YSeparates very bright peaks from detected source regions.50000 cd/m2 is the documented default. Do not lower it simply because a room is dim. Keep it above the source threshold in this interface and inspect the check image, especially for separated bright peaks. [1,3]
Merging angle -rGroups already detected candidate pixels into sources.0.2 rad (11.46 degrees) is the documented default. It does not decide whether a pixel crosses the detection threshold. Smaller values may separate nearby groups or fragment an extended source. [1,3,5]

The manual and Wienold's 2024 Discourse reply call -r a search radius; slide 71 of the 2023 tutorial calls it a search diameter. This interface labels it merging angle (-r) and passes the numeric argument unchanged. It does not resolve that terminology discrepancy by secretly doubling or halving it.

There is no universal daylight/electric or bright/dim parameter table in these materials. In the specific bright linear-reflection example on Discourse, Wienold suggested task multipliers from 5 up to 20, or fixed thresholds of 5000 or 10000 cd/m2, while leaving the merging parameter at its default. Those are scene-specific examples, not prescriptions for all well-lit interiors. For dim scenes, inspect a task-based reference rather than assuming that 2000 is automatically appropriate; the finite-range guard below matters. Do not tune thresholds just to obtain a preferred comfort score. [3,5]

Before assuming a bright source was missed, inspect its table row and the check image at an appropriate display exposure. Very bright source colors can appear white in a display preview. [5]

Use a laptop or other saved region as the task

In the existing Measure regions toolbar, draw the task as a rectangle, circle or polygon and save a named region, for example Laptop task. In the glare panel open Source detection and numerical settings, select Saved task region x multiplier, choose that record, and begin with multiplier 5. The panel shows the angular mean and resulting threshold. Then prepare and run glare normally.

Task mean = sum(Li ΔΩi) / sum(ΔΩi)
Detection threshold = multiplier x task mean

This is a solid-angle-weighted mean, not a cosine-weighted mean. For illuminance, cosine weighting is additional; it is not part of the average luminance. This distinction is explicitly confirmed by Wienold in the supplied 2025 discussion. [6]

The application recalculates the saved region from current calibrated source pixels, including its saved viewing-field intersection, and passes the threshold to the unmodified engine as a fixed -b value. The complete prepared view still supplies all potential sources and image-derived illuminance. Task selection does not rotate gaze, crop the analysis, exclude glare sources elsewhere, simulate adaptation, or change the background definition -q 0. Automatic target/background subtraction is not applied to the task: the saved shape itself is used.

This is an explicit application extension of the scalar task-reference concept. It is not native circular -t, not the post-detection -A mask, and not a claim that arbitrary task shapes have been validated against native task circles. Native -t/-T uses a center and angular extent; the latter colors that circle. Neither changes viewing direction. [1,3]

Dim-task boundary: the derived threshold must exceed 100 cd/m2. Native -b values of 100 or less mean multipliers, not absolute thresholds. This adapter stops instead of clamping the threshold or accidentally using the scene average. The engine's native circular task mode can express lower thresholds, but it is not implemented by this polygon adapter. Do not inflate the task multiplier merely to bypass this guard. [1]

Screen content and the exact chosen region matter: a full screen containing dark and light areas is a different task reference from a white document patch. Record what was selected. Saving the task does not establish how a participant actually looked at the scene. Glare source detection without a task is still meaningful within the selected method: fixed-threshold detection is itself the published default. [2,3]

The task record, shape, saved viewing field, angular mean, solid angle, multiplier and exact engine arguments are stored with the prepared analysis and exported JSON. Renaming or tinting a record does not alter a prepared calculation. Deleting the active task, changing its numerical measurement, changing multiplier, source calibration or geometry invalidates that calculation.

Background luminance and independent lux

Background Lb = (Ev - Edir) / π   [-q 0]
Eye-plane Ev = sum(Li max(0, n · ri) ΔΩi)

Background luminance for UGR/CGI is not the task average. The 2024 slides distinguish these quantities and explain that this background choice does not set DGP adaptation, which uses illuminance. [2]

A meter comparison needs the same position, receiving-plane normal and lighting state. Small orientation differences change cosine weighting; a reading made afterward may also sample a changed scene. Leave measured lux blank when checking the independent image estimate. Entering a measured lux value overrides the illuminance supplied to DGP; it does not recalibrate HDR pixels. This option and its separate image-derived reading are retained unchanged.

Glare impression: what can be inferred?

Evalglare reports both UGR and VCP. VCP is an estimated percentage of observers accepting a specified lighting arrangement from a specified position and direction. It is not an imperceptible-to-intolerable severity scale. UGR is a different discomfort-glare index; any attached verbal scale must identify its convention and application domain. Numeric availability alone does not establish that a metric is valid for daylight windows, very dim scenes, highly nonuniform small sources, or people with low vision. [3,7]

For example, AGi32's UGR documentation gives a historical convention with anchors such as 13 (just perceptible), 19 (just acceptable), and 25 (just uncomfortable), alongside specific limitations on correlating UGR and VCP. This guide does not apply these as automatic scene ratings. The supplied 2023 tutorial also contrasts daylight behavior among metrics. [3,8]

A visual halo or veil cannot be uniquely reconstructed from a scalar discomfort index. Evalglare's separate veiling-luminance outputs could support a separately defined disability-glare model, but that would need its own optical/adaptation assumptions and verification. It is not enabled here. The 2023 slides (pages 11-13) themselves caution about Stiles-Holladay applicability at high daylight adaptation. [3,9]
