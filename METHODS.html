HDR WORKSPACE 0.3.0

Prepare the image. Preserve the evidence.

This standalone static website accepts HDR images, EXR images, ordinary photographs and JPEG exposure sequences. It does not modify or depend on the Blackmagic desktop simulator. All processing is local to the browser; no image upload service, account, analytics or GPU is required. The optional HEIC codec can be hosted locally or loaded from a pinned CDN only with operator permission.

Software tests are not camera or clinical validation. The browser visibility model is a luminance-only DeVAS-derived adaptation. The program does not establish an individual's experience, safe navigation, glare acceptability, or regulatory compliance.

1. Preparation workflow

Import or reconstruct → crop if needed → correct and confirm geometry → choose luminance scale → analyze and export. A file already cropped elsewhere does not need to be cropped again. Enter the geometry of that current raster directly. Imported view information is populated as a draft, not silently treated as lens calibration.

Pixel cropping copies an exact float32 subset without interpolation. It preserves the current luminance multiplier. Regions and simulations are cleared because their coordinates have changed. The latest crop can be undone; one prior raster is retained for that purpose. Crop history records dimensions, offsets and the original working-raster origin.

When geometry is known, the crop updates horizontal and vertical extent and the Radiance view shift/lift. For perspective projection, Hnew = 2 atan((Wnew/Wold) tan(Hold/2)). With top-left crop coordinate x, vsNew = (vsOld + (x+Wnew/2)/Wold - 0.5)/(Wnew/Wold). The vertical offset accounts for image coordinates increasing downward. These relations are checked by comparing rays before and after off-center crops. Unknown geometry remains unconfirmed; cropping does not invent a lens specification.

Header editing and reprojection are different. The Original HDR / header-only export replaces geometry records while copying the original encoded pixel payload and photometric records unchanged. It does not apply a session patch calibration or an analysis mask and is disabled after cropping. Prepared HDR exports the current raster and active scale, including its crop, using quantized RGBE/XYZE encoding. Keep originals.

Supported standard views are perspective (-vtv), equidistant/angular (-vta), hemispherical/orthographic (-vth) and stereographic (-vts). Equisolid is not hemispherical: it is stored as explicit VISIONSIM_GEOMETRY metadata rather than an incorrect standard VIEW. A separate angular-export operation actually resamples the source to a standard equidistant circle. It uses bilinear sampling, renormalizes weights at the valid circle edge, and rejects missing interior support. Reprojected output is not a substitute for the original measurement raster.

The circle helper converts a known lens diameter angle and circle center/radius into full-raster angular extents and offsets. It does not fit a real lens. Source projection, image circle, crop and angular calibration must come from the acquisition setup. A mask excludes pixels; a crop removes pixels. Neither operation is a lens-distortion correction.

3. Luminance interpretation and scale

Linear RGB is converted to CIE XYZ using stated chromaticities and white point. Missing EXR chromaticities are flagged and use a Rec.709/sRGB fallback. Radiance RGB without primaries uses its standard primaries/white convention. XYZE and explicitly selected standard XYZ use Y directly. The user must verify that the source is scene-linear; a file extension does not prove that.

Radiance channel values are divided by accumulated EXPOSURE and COLORCORR before analysis; 179 is then available as the file-convention scale. EXR may supply positive whiteLuminance. New sources start in relative mode. File-declared scaling and measured-patch scaling are alternatives, not cumulative operations.

A measured patch sets K = meter luminance / mean valid patch Y, and L = K Y. This is a single anchor, not independent radiometric validation. It does not correct nonlinear response, offsets, shading, clipping or spectral mismatch. Crop and view-header changes preserve K. Mask changes conservatively invalidate a patch calibration. Patch provenance retains the raster and origin on which it was measured.

Numeric RGB/Y are separate from previews. The display uses a global tone map and SDR canvas; exposure and false-color controls do not change measurements. Signed Y is retained in numerical analysis/PFM, shown magenta when negative, and clamped only for visibility filtering. RGBE export rejects negative/nonfinite channels instead of silently clipping them. Header-only export preserves the original encoded values.

4. Bracket reconstruction

The response estimator uses the Debevec–Malik log-response least-squares formulation with log irradiance eliminated, 512 deterministic spatial samples, triangular data weights squared in the fit, second-difference smoothing with lambda 20 and separate g(128)=0 channel anchors. Observations are aggregated into 256 code bins to avoid quadratic scaling in the number of exposures at each sample. Underdetermined or substantially nonmonotonic fits are rejected.

Exposure times must be positive, span at least one stop, and correspond to fixed aperture/ISO/white balance/development. The user confirms alignment, scene stationarity and sRGB JPEG processing. A merge is the exponential of weighted mean log irradiance; codes outside 5–250 contribute no weight. Every channel needs at least one contributing exposure for a pixel to be valid. Invalid pixels are excluded from statistics. Prepared HDR export is blocked if the current raster contains invalid bracket pixels; use PFM plus mask or a justified crop instead.

A weighted log-radiance SD over 0.5 stop is a descriptive disagreement flag, not a validated ghost detector or confidence interval. Fitting residuals are not independent response validation. Separately anchored channels do not establish calibrated color. Reusable JSON responses require compatible camera/development settings. This is not hdrgen and does not import its polynomial .rsp files. It also does not accept camera RAW/BRAW. Independently checked Photosphere, hdrgen or LumiLab HDR results can be imported directly.

5. Statistics and exports

Statistics use equal weighting of valid image pixels within the selected rectangle and circle mask. They are not solid-angle weighted and do not produce illuminance. SD is population SD; percentiles interpolate sorted float32 samples. P05–P95 is not a camera dynamic-range measurement.

For regional means A (target) and B (background), Weber contrast is (A-B)/B; the two-region Michelson comparison is |A-B|/(A+B); the ratio is max(A,B)/min(A,B). Invalid physical inputs or zero denominators produce undefined results rather than a fabricated finite score.

JSON records source identity, interpretation, applied geometry, crop history, scale evidence, masks, saved regions and completed simulation. Complete-file SHA-256 is included where the browser secure context supports it; unavailable hashing is labeled. CSV exports regional measurements. PFM stores signed float32 luminance, little-endian and bottom-up, with no embedded units. PGM stores the validity mask. Keep the JSON and mask with numerical images. Preview PNG is display-only. Prepared HDR preserves current color primaries and scale convention; RGBE quantization means it is not a bit-exact archival replacement. Source photographs are not bundled with the application.

6. Reduced-detail visibility

A confirmed source projection supplies rays to a narrow perspective analysis viewport. The 4:3 viewport uses 256×192 or 512×384 pixels and 5–60° horizontal extent, bilinear sampling and 2×2 subpixel integration. It must lie within valid support. Yaw and pitch are relative to the original optical axis; view position/direction/up are preserved for file interchange. Optical resolution, source sampling and interpolation can impose stricter limits than the displayed viewport Nyquist check.

The clinical conversion is Smax = 2*10^PR - 1. Reference normal peak sensitivity is 199 at 0.914 cycles/degree, with asymmetric log-parabola slopes 0.68 and 1.28. The nominal cutoff is approximately 13.979 cycles/degree and scales by 10^(-logMAR). Peak frequency changes with contrast sensitivity to preserve the requested cutoff. Interface ranges are PR and logMAR 0–2.

The luminance-only adaptation uses raised-cosine octave bands, local contrast thresholding, sign-separated feathering and reflected, power-of-two FFT support. Angular frequency is approximated by a global width/HFOV scale within the limited viewport. Absolute mode uses the reference's 0.01 cd/m² denominator floor; relative mode explicitly substitutes one millionth of padded-image mean to make numerical scaling consistent. This is not the unmodified DeVAS executable. The two previews share one display transform. The model does not include chromatic visibility, adaptation, glare, field loss, hazard geometry, individual disease progression or navigation performance.

7. Version 0.3 validation boundary

The release includes retained numerical suites for filtering, codecs, geometry and streaming brackets, plus new tests for FOV, orientation, gain metadata, false-color endpoints/ticks, and educational effects. The new browser suite exercises actual JPEG base/gain decoding and floating-point reconstruction using generated Adobe, ISO and Apple-XMP fixtures. These are deterministic test containers, not a representative survey of phone exports.

The supplied Canon/Photosphere room HDR and EXR, and the separate-scene ten-JPEG bracket, were tested independently. Core regression, six sample-specific stages, and a 16-exposure synthetic merge passed. A first combined run exceeded the execution time limit; the complete rerun passed. Test results and SHA-256 checks are supplied with the release.

HEIC is conditional, not end-to-end validated here. Container inspection, transfer-function math and the high-bit-depth adapter contract were tested; the actual external libheif WASM binary could not be downloaded in this environment. Neither a mock decoder nor an uncompressed HEIF fixture constitutes HEVC validation. Unsupported Adaptive HDR HEIF tmap is rejected. Install/permit the codec and test a representative file before relying on this route.

Browser testing used production bundles in an in-memory Chromium page because network navigation is blocked in this environment. Worker and resource-base URLs were substituted for that test harness. This is not live-host acceptance testing. Firefox, Safari, physical mobile hardware, camera/meter accuracy and human-observer validity have not been tested. Narrow-window layout testing is not physical-device testing.

9. Metadata-assisted rectilinear FOV

The calculator uses HFOV = 2 atan(Sw/(2f)) and VFOV = 2 atan(Sh/(2f)), converted to degrees, with actual focal length and active sensor dimensions. Resizing alone does not alter FOV. Portrait orientation swaps axes. In-app crop history is then applied with the existing ray-preserving crop geometry.

Full-frame, typical APS-C variants, Micro Four Thirds and editable sensor dimensions are offered. EXIF focal-plane resolution can supply an estimate; the exact Canon EOS 6D preset is recognized. This is not a comprehensive camera/smartphone sensor database. Camera manufacturer alone never selects a sensor. EXIF 35-mm-equivalent focal length uses an explicitly documented diagonal-equivalence convention at the current aspect ratio. Computational crop, zoom and differing manufacturer conventions must be reviewed. An aspect mismatch requires active dimensions or confirmation of a centered aspect crop; the tool does not invent the missing crop.

A metadata estimate is a draft, never automatically confirmed. Use the calculator only for rectilinear lenses. A fisheye still requires its actual projection and known angular diameter/image-circle geometry. Lens distortion and focus breathing are not fitted.

10. Luminance false color

False color is applied to the source Y times the active calibration scale, not to its tone-mapped preview or a simulated condition. Linear mapping uses t = (L - min)/(max - min); logarithmic mapping uses t = (ln L - ln min)/(ln max - ln min). The log minimum must be strictly positive; linear ranges may start at zero. The minimum must be finite, nonnegative and smaller than the maximum. Changing palette, range or display EV does not change measurements.

Available controls include editable endpoints, linear/log scales, continuous or stepped bands, palette selection, legend intervals, range presets, Auto P05-P95, full sampled-data range and a range lock for successive inputs. The spectrum palette is Photosphere-like, not a verified reproduction of its precise color lookup table. The legend uses the same mapping as the image. Linear ticks are arithmetically spaced and log ticks geometrically spaced. If zero is in the data and log full-range is requested, the interface states the positive plotting floor.

Outside-range black/white markers are optional; negative values are magenta and invalid/excluded support is checkerboard. Negative/invalid values are not converted to valid zero measurements. The PNG export includes the applied legend, range, units and scale status. Its pixels remain a display visualization. The JSON retains the display configuration; PFM and validity masks retain the numerical record.

11. Phone-image import

Built-in JPEG handling identifies supported Adobe/Android XMP 1.0, ISO 21496-1 metadata, and Apple XMP HDRGainMapHeadroom. It decodes base/gain JPEG planes separately, linearizes the supported source profile, bilinearly samples the gain image, reconstructs float32 light values, then applies EXIF orientation. HDR values can exceed SDR white. It does not let an 8-bit canvas silently replace the numerical HDR result.

For supported SDR-base gain maps at full encoded headroom, logGain = min + (max-min) * encodedGain^(1/gamma) and HDR = (linearSDR + offsetSDR) * 2^logGain - offsetHDR. The supported Apple XMP convention maps its explicit linear headroom to log2 maximum gain. Older Apple HEIC auxiliary gain is a different convention, requiring its own headroom metadata and transfer function. HDR-base/backward maps, alternate application color spaces and unrecognized gain conventions are rejected rather than silently flattened. SDR base only is an explicit, recorded choice.

Reconstructed phone HDR is rendered HDR, not a recovered calibrated scene. Computational camera tone mapping remains. No scene cd/m2 is inferred from HDR white/headroom. PQ values represent display light and are normalized to a 203-nit reference for relative analysis; HLG uses the inverse OETF without assuming a display OOTF. A meter anchor can match one target but does not undo camera processing.

HEIC/HEIF uses the optional libheif-js adapter. SDR, PQ/HLG and a legacy Apple auxiliary-gain route are implemented but require actual-codec/device-file validation. ISO Adaptive HDR HEIF tmap is not supported by this release. Files with unsupported color profiles, transparency or missing needed HDR metadata stop with an explanation. Only decoder code may be requested from an operator-approved CDN; image bytes are not uploaded by this application.

12. Educational color-condition previews

The new panel reprojects a color viewport from the same source and confirmed geometry. It offers cataract-like haze/yellowing, peripheral-field restriction, central loss, deterministic scattered loss, red-green/blue-yellow/monochromatic color-deficiency illustrations, and custom blur/contrast/saturation. These are educational effects, not patient-specific disease models or validated disease-severity scales. Graphical dim/black regions mark altered image information; they are not a claim that a person literally perceives black patches. Fixation remains user-defined, not eye-tracked.

Field diameters are angular and use ray separation; custom blur sigma is in degrees with a viewport-center sampling approximation. Color-deficiency matrices follow Machado et al. (2009), interpolated in linear RGB. Scattered loss uses a recorded seed for reproducibility. The optional reduced-detail step applies the existing DeVAS-derived luminance filter before the illustrative condition; the color recombination is not the original DeVAS chromaticity filter. Both preview panels share one tone-mapping anchor. Source arrays, source regional measurements and false color remain unchanged.

Educational exports are labeled comparison PNGs, with model/settings recorded in analysis JSON. They are not new measured luminance images, hazard scores or clinical assessments.
